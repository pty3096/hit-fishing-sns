# 앱 안 알림 — 0.11.0

상단 종 아이콘에서 내 조황에 달린 댓글·좋아요와 새 팔로워 소식을 확인합니다. 로그인·이메일 인증을 완료한 본인만 볼 수 있습니다. 본인이 자기 조황에 남긴 댓글·좋아요는 알림을 만들지 않습니다. 적용 이전 활동은 소급해 알림으로 만들지 않습니다.

## 읽음과 갱신

종 아이콘에 현재 보이는 미확인 알림 수를 표시합니다. 100개 이상은 `99+`로 줄여 표시합니다. 화면을 열거나 알림 화면의 새로고침 버튼을 누르면 갱신하며, 실시간 스트리밍·주기적 자동 새로고침·아이폰 푸시·이메일 알림은 포함하지 않습니다.

알림의 조황 확인·프로필 확인 버튼을 누르면 해당 알림을 읽음 처리하고 대상 화면으로 이동합니다. 모두 읽음은 화면을 열었을 때의 가장 최신 알림 번호까지만 처리합니다. 그 뒤 도착한 새 알림은 미확인 상태로 남깁니다. 한 번에 20개씩 최신 순으로 조회하고 이전 알림을 더 불러올 수 있습니다. 실패한 추가 조회는 다시 시도할 수 있습니다.

## 데이터와 공개 범위

SQLite 트리거로 댓글·좋아요·팔로우 생성과 같은 트랜잭션 안에서 알림을 기록합니다. 댓글 재시도와 반복 PUT은 알림을 중복 생성하지 않습니다. 댓글 삭제·원글 삭제·좋아요 취소·팔로우 취소 시 해당 알림도 정리됩니다. 취소 후 새로 좋아요·팔로우하면 새 알림을 만듭니다. 양쪽 사용자 탈퇴 시 관련 알림을 삭제합니다.

목록과 미확인 수 모두 차단·이용 제한된 사용자, 숨김된 원글·댓글을 제외합니다. 다시 볼 수 있는 상태가 되면 남아 있는 알림이 재표시될 수 있습니다. 타인 계정 번호나 알림 번호를 지정해도 목록·읽음 상태에 접근할 수 없습니다. 알림에는 원문 댓글·이메일·사진을 중복 저장하지 않고 관련 사용자·조황·댓글 번호와 종류·읽음 상태·생성 시각만 저장합니다. 스키마 버전은 9입니다.

## API

- `GET /api/notifications`: 내 목록·미확인 수, `before`로 이전 목록 조회
- `GET /api/notifications?summary=1`: 내 미확인 수
- `PUT /api/notifications/:id/read`: 본인에게 보이는 알림 한 개 읽음
- `PUT /api/notifications/read`: `through_id`까지 본인에게 보이는 알림 읽음

## 검증과 적용 기록

자동 검사 30개 통과. 세 계정의 목록 분리·타인 읽음 거절, 본인 활동 제외, 댓글 재시도·반복 좋아요·팔로우, 서버 재시작 후 보존, 새로 도착한 알림을 남기는 읽음 범위, 취소·삭제·숨김·차단·이용 제한·탈퇴 처리, 20개 페이지 경계를 확인했습니다.

브라우저에서 종 아이콘 연결·빈 목록·새로고침과 모바일 390px 가로 넘침 없음을 확인했습니다. 현재 개발 계정에 없는 활동을 실제 알림처럼 삽입하지 않았습니다. 실제 아이폰 조작은 추가 확인이 필요합니다.

초기 두 DB 동시 백업의 시간 기반 이름이 충돌해 실패했습니다. 적용 후 로컬·시범 DB를 서로 다른 명시적 이름으로 백업하고 무결성 검사를 완료했습니다. 이후 기본 백업 이름에 원본 파일 이름과 무작위 UUID를 포함하도록 보완했습니다. 적용 전 백업이 성공했다고 기록하지 않습니다. 기존 계정·조황·사진은 보존했고 비공개 자료는 GitHub에 올리지 않습니다.
